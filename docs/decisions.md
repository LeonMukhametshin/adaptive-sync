# Журнал решений

Решения из таблицы «Принятые решения по умолчанию» плана (стек, предметная модель, хранение полей вне K(v)
только на сервере, tombstone при удалении старым клиентом, HTTP + JSON, seed и логические часы) здесь не повторяются.
Ниже — решения, принятые по ходу реализации.

| Дата | Задача | Решение | Почему |
| --- | --- | --- | --- |
| 2026-10-15 | DMS-1 | Решение .NET лежит в подпапке `adaptive-sync/` рядом с Unity-проектом; `docs/` — в корне репозитория. | Unity не трогает папки вне `Assets/`, а `Directory.Build.props` решения не влияет на сгенерированные Unity `*.csproj`. |
| 2026-10-15 | DMS-1 | `.gitignore` игнорирует `*.csproj` и `*.sln` только в корне (их генерирует Unity), проекты в `adaptive-sync/` коммитятся. | Иначе проекты решения не попадают в репозиторий. |
| 2026-10-15 | DMS-1 | `Sync.Core` и `Sync.Client` — netstandard2.1 и C# 9; сервер и тесты — .NET 8. | C# 9 — максимум, который компилирует Unity 6; DLL подключаются в `Assets/Plugins/` (DMS-3). |
| 2026-10-15 | DMS-1 | Реестр полей задан в коде (`SchemaVersions.Registry`) — единственный источник истины. DDL SQLite генерируется из него; миграции PostgreSQL написаны вручную, а тесты сверяют их столбцы с реестром. Таблица `schema_registry` заполняется из кода при каждом запуске миграций. | Ручные миграции v1 → v2 → v3 показывают эволюцию схемы для статьи, а сверка тестами исключает расхождение. |
| 2026-10-15 | DMS-1 | Поля, которых нет в таблице плана: `inventory_item.player_id` (uuid, FK на `player_profile`, scalar, обязательно), `inventory_item.item_type` (scalar), `item_modification.item_id` (uuid, FK на `inventory_item`, scalar, обязательно), `item_modification.mod_type` (scalar), `item_modification.mod_level` (scalar). | Нужны для связей и для данных v3; категория scalar — нейтральное LWW-правило. |
| 2026-10-15 | DMS-1 | Значения по умолчанию: `level` = 1, `coins` = 0, `settings_sound` = true, `premium_currency` = 0, `quantity` = 0, `durability` = 100, `mod_level` = 1; остальные поля допускают NULL. Новое поле в существующей таблице не может быть обязательным. | Значения по умолчанию получают поля вне K(v) в базовых стратегиях (LWW, Client Wins); старые клиенты должны вставлять записи без новых полей. |
| 2026-10-15 | DMS-1 | Целые поля — 64-битные (`bigint` / SQLite `INTEGER`). `deleted_at` хранит логическое время симулятора (`bigint`), а не `timestamptz`. | Детерминизм: системное время в логике синхронизации не используется. |
| 2026-10-15 | DMS-1 | Формат `field_versions`: `{"поле": {"v": row_version, "t": логическое время}}`. | Версия нужна для S3/S4 (менялось ли поле после `base_row_version`), время — для LWW по полю. |
| 2026-10-15 | DMS-1 | Клиентские таблицы SQLite содержат служебные столбцы `id`, `row_version`, `is_deleted`; `field_versions` и `deleted_at` есть только на сервере. Версия локальной схемы — в таблице `schema_info`. Обновление локальной схемы пока не поддерживается. | Конфликты разрешает сервер; клиенту достаточно версии записи, которую он видел. |
| 2026-10-15 | DMS-1 | В запрос добавлен курсор `SinceServerVersion`, в ответ — `ServerVersion`. | План требует возвращать изменения других клиентов с прошлой синхронизации; для этого нужен курсор. |
| 2026-10-15 | DMS-1 | `ISyncStrategy.Decide` не обращается к хранилищу: получает контекст клиента (K(v)), операцию и снимок серверной записи и возвращает решение по полям; применяет решение сервер. | Все стратегии получают одинаковый вход и тестируются юнит-тестами без БД. |
| 2026-10-15 | DMS-1 | Тесты PostgreSQL (Testcontainers) пропускаются, если Docker недоступен. | Остальные тесты можно запускать без Docker. |
| 2026-10-15 | DMS-1 | PostgreSQL из `docker-compose.yml` публикуется на порт хоста 55432, а не 5432. | На машине разработки порт 5432 занимает локально установленный PostgreSQL 12 для Windows, и подключения к `localhost:5432` попадали в него. |
| 2026-10-15 | DMS-2 | Новый проект `Sync.Strategies` (netstandard2.1, C# 9) для реализаций `ISyncStrategy`; стратегия на сервере выбирается настройкой `Sync:Strategy` (по умолчанию `ServerWins`). | Структура из плана; стратегии меняются одной настройкой и тестируются без БД. |
| 2026-10-15 | DMS-2 | `row_version` — значение глобальной последовательности `sync_row_version_seq`, общей для всех таблиц. Курсор `SinceServerVersion` — последнее выданное значение; изменения других клиентов — строки с `row_version` больше курсора. | Один монотонный счётчик даёт и версию записи для конфликтов, и курсор изменений без отдельного журнала. |
| 2026-10-15 | DMS-2 | Сеансы `/sync` сериализуются блокировкой `pg_advisory_xact_lock`, весь запрос обрабатывается в одной транзакции. | Без параллельных сеансов курсор не пропускает изменения, а результат воспроизводим; для эксперимента пропускная способность не важна. |
| 2026-10-15 | DMS-2 | Идемпотентность: исход каждой операции пишется в `sync_operation_log` (ключ `op_id`, плюс решения по полям в `fields`). Операция с известным `op_id` не применяется повторно, клиенту возвращается сохранённый результат. | Повторная отправка пакета (например, после потерянного ответа) не дублирует изменения; журнал пригодится для метрик. |
| 2026-10-15 | DMS-2 | Последовательные операции клиента над одной записью в одном пакете: если запись была изменена предыдущей операцией этого же пакета, её новая версия считается базовой для следующей. | Иначе вторая офлайн-правка новой записи (база 0) отклонялась бы как конфликт с собственной вставкой. |
| 2026-10-15 | DMS-2 | Server Wins определяет конфликт на уровне записи: `row_version` на сервере больше `base_row_version` → вся операция отклоняется. Отклонённые операции удаляются из журнала клиента, локальная запись перезаписывается состоянием сервера. | Соответствует базовой стратегии «запись целиком, конфликтующие изменения клиента отклоняются». |
| 2026-10-15 | DMS-2 | Удаление на сервере — пометка `is_deleted = true`, `deleted_at` = логическое время операции; физически строка не удаляется. Отличие обычного удаления от tombstone фиксируется исходом в `sync_operation_log`. | Удаление должно доходить до других клиентов через курсор; для этого строка нужна. |
| 2026-10-15 | DMS-2 | Ошибки протокола уровня операции (поле вне K(v), таблица не из схемы клиента, неверный тип значения) — исход `Rejected` с сообщением `Protocol error`; ошибки уровня запроса (неподдерживаемая версия схемы, повтор `op_id`) — HTTP 400. Нарушение ограничений БД откатывается до точки сохранения операции и даёт `Rejected`. | Одна плохая операция не срывает весь пакет. |
| 2026-10-15 | DMS-2 | Клиент: журнал `op_journal` и курсор `sync_state` в той же SQLite-БД; изменения пишутся локально и в журнал одной транзакцией. Офлайн `SyncAsync` бросает `InvalidOperationException` без обращения к серверу. Ответ применяется по порядку таблиц реестра (родительские раньше дочерних). | Журнал переживает перезапуск; порядок таблиц не нарушает внешние ключи SQLite. |
| 2026-10-15 | DMS-2 | Идентификаторы записей и операций на клиенте берутся из генератора `Func<Guid>`; для тестов и симулятора — `DeterministicGuids.FromSeed`. Логическое время задаёт `LogicalClock`, общий для клиентов одного сценария. | Детерминизм: без `Guid.NewGuid()` и системного времени в логике синхронизации. |
| 2026-10-15 | DMS-2 | JSON протокола — `System.Text.Json` (web-настройки, enum строками) в `Sync.Core`; значения полей приводятся к типам реестра через `FieldValues.Normalize` (text → string, integer → long, boolean → bool, uuid → Guid). | Один формат для клиента и сервера; зависимость пакета подключится в Unity вместе с DLL (DMS-3). |
| 2026-10-15 | DMS-2 | Миграции сервера применяются в `IHostedLifecycleService.StartingAsync`, а не после `Build()`. | Код после `Build()` не выполняется под `WebApplicationFactory`, а интеграционные тесты поднимают сервер через неё. |
| 2026-10-15 | DMS-3 | Сервер синхронизации собирается в Docker-образ (`src/Sync.Server/Dockerfile`) и запускается сервисом `server` в `docker-compose.yml` на порту хоста 5080 вместе с PostgreSQL. | По плану DMS-3 сцена Unity синхронизируется с сервером из Docker; `docker compose up` поднимает весь стенд. |
| 2026-10-15 | DMS-3 | DLL для Unity собирает `adaptive-sync/build-unity-plugins.ps1`: `dotnet publish Sync.Client -r win-x64` и копирование в `Assets/Plugins/AdaptiveSync` (управляемые сборки) и `Assets/Plugins/AdaptiveSync/x86_64` (нативная `e_sqlite3.dll`). Собранные DLL и их `.meta` коммитятся. | Проект Unity открывается без .NET SDK; после изменений в `Sync.Core`/`Sync.Client` скрипт запускается заново. |
| 2026-10-15 | DMS-3 | SQLite в Unity — `Microsoft.Data.Sqlite` + SQLitePCLRaw (`provider.e_sqlite3`) с нативной `e_sqlite3.dll`; зависимости `System.Text.Json` (`System.Memory`, `System.Buffers` и др.) кладутся рядом. Проверено в редакторе Unity 6000.0.64f1 (Mono, Windows x64): конфликтов сборок нет. | Тот же клиент, что в интеграционных тестах, без отдельной обёртки. |
| 2026-10-15 | DMS-3 | Платформы: нативная библиотека настроена только для Editor и Standalone Win64. Для IL2CPP добавлен `Assets/AdaptiveSync/link.xml`, но сборка IL2CPP не проверялась (модуль IL2CPP для Windows не установлен); Android, iOS и macOS не поддерживаются. | Unity — демо-оболочка, эксперименты идут в симуляторе на .NET; другие платформы — отдельная задача при необходимости. |
| 2026-10-15 | DMS-3 | Демо-сцена `Assets/Scenes/SyncDemo.unity` создаётся меню `Adaptive Sync/Create SyncDemo Scene`; интерфейс — IMGUI в `SyncDemo`, логика — в `SyncDemoSession` (без MonoBehaviour). Локальная БД — `persistentDataPath/adaptive-sync-unity-v{N}.db`. | Сцена воспроизводима из кода и не требует ручной вёрстки; логику можно тестировать без сцены. |
| 2026-10-15 | DMS-3 | В интерактивном демо идентификаторы берутся из `Guid.NewGuid`, в Play Mode тесте — из `DeterministicGuids` с seed, уникальным для прогона. | Сервер общий и хранит данные между запусками: одинаковые `op_id` при перезапуске демо или теста совпали бы с уже записанными операциями. | 2026-10-15 | DMS-3 | Play Mode тест повторяет сценарий профиля из интеграционного теста DMS-2 против сервера `http://localhost:5080/` (переопределяется переменной `ADAPTIVE_SYNC_SERVER`) и помечается Ignored, если сервер не запущен. | Критерий DMS-3 — совпадение результата с DMS-2 на сервере из Docker. |
| 2026-10-15 | DMS-4 | LWW и Client Wins эмулируют отправку «записи целиком»: при победе клиента пишутся его изменённые поля, неизменённые поля из K(v) сохраняют текущее серверное значение, поля вне K(v) получают `DefaultValue` из реестра (исход поля `Overwritten`). | Протокол передаёт только изменённые поля; потеря полей вне K(v) — именно то, что должна показать базовая стратегия уровня записи. |
| 2026-10-15 | DMS-4 | Логическое время записи для LWW — максимум `t` в `field_versions`; при равном времени побеждает сервер. Field-level LWW сравнивает время операции с `t` каждого поля; поле без записи в `field_versions` имеет время 0. Удаление в Field-level LWW проходит, только если операция новее всех полей записи. | Детерминированное правило без системного времени. |
| 2026-10-15 | DMS-4 | Все стратегии отклоняют `update` и `delete` удалённой или отсутствующей записи; `insert` поверх существующей записи — отказ в Server Wins, перезапись в LWW (если операция новее) и Client Wins, слияние по полям в Field-level LWW. | Одинаковая обработка граничных случаев, чтобы различия стратегий сводились к правилам S1–S5. |
| 2026-10-15 | DMS-4 | Таблица поведения стратегий в S1–S5 ведётся в `docs/method.md` (раздел «Базовые стратегии») и совпадает с тестами `BaselineSituationTests`. | Материал сразу пригоден для раздела статьи «Метод». |
| 2026-10-15 | DMS-5 | Вход оракула — начальные записи и журнал событий в порядке доставки на сервер. У события есть автор (клиент или `server`), версия схемы, операция, изменения полей (старое и новое значение) и три момента логического времени: `MadeAt` (когда сделано), `SeenAt` (какое состояние сервера автор видел перед изменением), `DeliveredAt` (когда доставлено). | Этого достаточно, чтобы определить конфликт и S1–S5 без знания стратегий; симулятор (этап 7) знает все три момента. |
| 2026-10-15 | DMS-5 | Конфликт по полю (S4): другой автор доставил изменение того же поля после `SeenAt` события и раньше него. События с автором `server` применяются сразу (`SeenAt = MadeAt = DeliveredAt`) и сами конфликтом не считаются. | Формализует «обе стороны независимо изменили одно поле» через порядок доставки. |
| 2026-10-15 | DMS-5 | S3: клиент старше последней версии, конфликта по полю нет, но после `SeenAt` были доставлены изменения полей вне K(v) этой записи. Иначе старый клиент — S2, клиент последней версии — S1. | Классификация по каждому полю операции; S4 имеет приоритет. |
| 2026-10-15 | DMS-5 | Правила S4 в оракуле: counter — сохранённое значение + (новое − старое) входящего изменения; user_owned и user_preference — побеждает входящее (синхронизирующийся клиент); server_authoritative — сохраняется значение сервера; scalar — LWW по `MadeAt`, при равенстве сохраняется значение сервера. | «Приоритет клиента/сервера» из плана трактуется как «входящее изменение / уже сохранённое значение». |
| 2026-10-15 | DMS-5 | S5: удаление клиентом старше последней версии, если у записи есть поле вне K(v) со значением, отличным от `DefaultValue`, или неудалённая связанная запись в таблице, появившейся после v. Эталон — tombstone: запись помечена удалённой, все значения и связанные записи сохранены. Удаление в остальных случаях — обычное (S1/S2), конфликт на удалении не проверяется. | «Непустое значение» = отличное от умолчания: иначе счётчики с умолчанием 0 делали бы любую запись «с данными». Зависит от решения 4 плана, которое ещё подтверждается. |
| 2026-10-15 | DMS-5 | Изменения и удаления уже удалённой или отсутствующей записи оракул пропускает без классификации; вставка существующей записи обрабатывается как изменение её полей. | Граничные случаи не входят в критерии S1–S5 и не должны влиять на метрики. |
