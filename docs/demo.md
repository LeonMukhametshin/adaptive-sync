# Сценарий демонстрационного видео

Видео отвечает на запрос научного руководителя: показать работу метода — синхронизацию клиентов разных версий (В1),
разрешение конфликтов (В2), сохранение данных, неизвестных старой версии клиента (В3), обработку удаления записей (В4) —
и отличие от одной базовой стратегии (В5). Базовая стратегия — **Client Wins**: она отличается от метода в S3, S4 и S5.
Длительность — 8–10 минут.

Во всех эпизодах используются два профиля автора:
- **Leon** — создан клиентом v3: монеты 111, аватар `avatar_default`, премиальная валюта 222, регион `RU`;
- **Profile 2** — создан клиентом v3: монеты 100, аватар `avatar_second`, премиальная валюта 10, регион `EU`.

Метод показывается на профиле **Profile 2**, базовая стратегия — на профиле **Leon**. Серверную базу между эпизодами
не очищать.

## Обозначения

- «Настройки → v1» — вкладка «Настройки», карточка «Клиент», кнопка «v1 · старая схема» (для v3 — «v3 · текущая схема»).
- «Стратегия X» — «Настройки», карточка «Стратегия сервера», чип «Адаптивный» или «Client Wins».
- «Синхр.» — вкладка «Синхронизация», кнопка «Синхронизировать».
- «Офлайн/Онлайн» — вкладка «Синхронизация», переключатель в карточке «Сеть». Состояние сети сохраняется при смене
  клиента: после переключения на другого клиента проверить переключатель.
- `profiles`, `decisions`, `health` — команды из `adaptive-sync/demo.ps1` в окне PowerShell.

## 0. Подготовка (до записи)

1. Запустить Docker Desktop, дождаться «Engine running».
2. PowerShell в папке `adaptive-sync`:
   ```powershell
   docker compose up -d --wait
   . .\demo.ps1
   health
   ```
   Ожидается `"strategy":"Adaptive","strategySource":"resolver"`. Если `docker compose` завис —
   `docker start adaptive-sync-postgres`.
3. Unity: сцена `Assets/Scenes/Boot.unity`, окно Game в режиме **Simulator**, Play.
4. OBS: окно Unity и окно PowerShell рядом, крупный шрифт PowerShell, микрофон. Открыть `docs/results/summary.md`
   и графики `docs/results/charts/old-share-loss.svg`, `offline-lost-increments.svg`.

## Запись

### Эпизод 1. Постановка и стенд (≈1 мин) — контекст

1. PowerShell: `docker ps` — три контейнера: PostgreSQL, сервер синхронизации, resolver.
2. «Настройки»: строка «Сервер доступен · схема сервера v3, клиента v… · стратегия Адаптивный (сервис resolver)» уже
   показана (сервер проверяется при запуске). «Проверить соединение» — всплывёт «Соединение проверено · стратегия
   Адаптивный».

> Клиент хранит данные локально в SQLite и работает без сети; сервер хранит основную копию в PostgreSQL. Одновременно
> работают клиенты разных версий схемы: клиент v1 не знает полей avatar_id, premium_currency (v2) и region (v3).
> Решение по конфликтам принимает сервис resolver; его можно переключить на базовую стратегию.

### Эпизод 2. Синхронизация клиентов разных версий (≈1 мин) — **В1**

1. Клиент v3: «+ Новый профиль» — `Leon`, 111, `avatar_default`, 222, `RU` → «Сохранить» → «Синхр.».
   Затем второй профиль — `Profile 2`, 100, `avatar_second`, 10, `EU` → «Сохранить» → «Синхр.».
2. «Настройки → v1» → «Синхр.» — получены оба профиля. Открыть `Profile 2`: только Никнейм и Монеты и подсказка
   «Клиент v1 не знает полей avatar_id, premium_currency, region…» → «Отмена».
3. PowerShell: `profiles` — на сервере у обоих профилей все поля.

### Эпизод 3. Сохранение данных, неизвестных старой версии (≈2,5 мин) — **В3, В5**

Метод (стратегия «Адаптивный», профиль `Profile 2`):
1. Клиент v1 → **Офлайн**. `Profile 2` → Никнейм `Profile 2222` → «Сохранить».
2. «Настройки → v3» → **Онлайн**. `Profile 2`: Аватар `avatar_second222`, Регион `US` → «Сохранить» → «Синхр.».
3. «Настройки → v1» → **Онлайн** → «Синхр.» → **Applied**, «S3 · сервер менял неизвестные клиенту поля — они сохранены»,
   `nickname — применено (S3)`.
4. «Настройки → v3» → «Синхр.» → у профиля ник `Profile 2222`, аватар `avatar_second222`, регион `US`. PowerShell: `profiles`.

> Старый клиент изменил только известную ему часть записи, а поля, о которых он не знает, сохранились.

Базовая стратегия («Настройки» → «Client Wins», профиль `Leon`):
5. «Настройки → v1» → **Офлайн**. `Leon` → Никнейм `Leon 2` → «Сохранить».
6. «Настройки → v3» → **Онлайн**. `Leon`: Аватар `avatar_new`, Регион `EU` → «Сохранить» → «Синхр.».
7. «Настройки → v1» → **Онлайн** → «Синхр.» → **Applied**, `nickname — применено` и `avatar_id`, `premium_currency`,
   `region` — «затёрто значением по умолчанию».
8. PowerShell: `profiles` — у `Leon 2` аватар и регион пустые, премиальная валюта 0 (было 222).

> Client Wins перезаписывает запись целиком: старый клиент затёр данные, о которых даже не знает.

⏸ **Пауза записи.** «Стратегия Адаптивный»; «Настройки → v3» → «Синхр.»; «Настройки → v1» → «Синхр.» — оба клиента
получили последние версии профилей. Оставить выбранным v1, сеть Онлайн.

### Эпизод 4. Разрешение конфликта (≈1,5 мин) — **В2, В5**

Метод (стратегия «Адаптивный», профиль `Profile 2222`, монеты 100):
1. Клиент v1 → **Офлайн**. `Profile 2222` → Монеты `130` (+30) → «Сохранить».
2. «Настройки → v3» → **Онлайн**. `Profile 2222` → Монеты `150` (+50) → «Сохранить» → «Синхр.».
3. «Настройки → v1» → **Онлайн** → «Синхр.» → **Merged**, «S4 · конфликт решён по категории поля»,
   `coins — слито с серверным значением (S4)`.
4. PowerShell: `profiles` — у `Profile 2222` монеты **180** = 100 + 50 + 30, аватар и регион на месте.

Базовая стратегия («Client Wins», профиль `Leon 2`, монеты 111):
5. Клиент v1 → **Офлайн**. `Leon 2` → Монеты `141` (+30) → «Сохранить».
6. «Настройки → v3» → **Онлайн**. `Leon 2` → Монеты `161` (+50) → «Сохранить» → «Синхр.».
7. «Настройки → v1» → **Онлайн** → «Синхр.» → **Applied**, `coins — применено`.
8. PowerShell: `profiles` — у `Leon 2` монеты **141**: приращение +50 другого клиента потеряно.

> Оба клиента меняли одно поле. Метод учитывает категорию: coins — счётчик, поэтому приращения складываются. Для полей
> пользователя побеждает клиент, для серверных — сервер, для скалярных — последнее изменение по логическому времени.

⏸ **Пауза записи.** «Стратегия Адаптивный»; «Настройки → v3» → «Синхр.»; «Настройки → v1» → «Синхр.». Оставить v1, Онлайн.

### Эпизод 5. Удаление записи старым клиентом (≈1,5 мин) — **В4, В5**

1. Стратегия «Адаптивный». Клиент v1: `Profile 2222` → «Удалить профиль» → «Синхр.» → **Tombstoned**,
   «S5 · удаление старым клиентом: tombstone, данные сохранены»,
   «Tombstone keeps data unknown to v1: avatar_id, premium_currency, region».
2. «Настройки» → «Client Wins». Клиент v1: `Leon 2` → «Удалить профиль» → «Синхр.» → **Applied** — обычное удаление.
3. PowerShell: `decisions` — строки удаления `Adaptive | 1 | Delete | Tombstoned | Tombstone keeps data…` и
   `ClientWins | 1 | Delete | Applied`. `profiles` — у `Profile 2222` `is_deleted = t`, а `avatar_second222`, `10`,
   `US` сохранены.

> Клиент v1 не видит часть данных записи, поэтому метод вместо удаления ставит tombstone и сохраняет данные новых
> версий. В прототипе удаление всегда «мягкое», поэтому разница — в решении сервера: базовая стратегия считает данные
> удалёнными, метод — сохранёнными.

### Эпизод 7. Итог (≈20 с)

> Метод учитывает одновременно версию схемы клиента, версии полей и категорию данных: применяет изменения старых
> клиентов только к известной им части записи, не теряет неизвестные им поля, автоматически решает конфликты по
> категориям и при удалении записи с новыми данными сохраняет их.

⏹ **Остановить запись.** Вернуть «Стратегия Адаптивный» (`health` → `"strategy":"Adaptive"`).
