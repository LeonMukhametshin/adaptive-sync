# Метод адаптивной синхронизации — материалы для статьи

## Базовые стратегии

Четыре стратегии для сравнения с адаптивным методом реализуют общий интерфейс `ISyncStrategy`
и получают одинаковый вход: версию схемы клиента и K(v), операцию журнала, снимок серверной записи
со значениями всех полей и `field_versions`. Логическое время записи — максимум времени изменения её полей;
при равенстве времени побеждает сервер.

| Стратегия | Уровень | Конфликт | Поля вне K(v) |
| --- | --- | --- | --- |
| Server Wins | запись | `row_version` сервера > `base_row_version` → операция клиента отклоняется | не изменяются |
| LWW | запись | побеждает бо́льшее логическое время | при победе клиента получают значения по умолчанию |
| Client Wins | запись | клиент всегда побеждает | получают значения по умолчанию |
| Field-level LWW без учёта схемы | поле | LWW по времени каждого поля | не изменяются; версия схемы не учитывается |

Поведение в ситуациях S1–S5 (зафиксировано тестами `Sync.Strategies.Tests/BaselineSituationTests`):

| Ситуация | Критерий (эталон) | Server Wins | LWW | Client Wins | Field-level LWW |
| --- | --- | --- | --- | --- | --- |
| S1: версии равны, конфликта нет | изменения клиента применены | применены | применены | применены | применены |
| S2: клиент старше, конфликта нет | применены, поля вне K(v) не тронуты | соответствует | поля вне K(v) сброшены к умолчаниям — потеря | поля вне K(v) сброшены — потеря | соответствует |
| S3: на сервере изменились поля вне K(v) | поля вне K(v) сохранены, изменения клиента применены | изменения клиента отклонены — потеря клиентских данных | серверные поля вне K(v) сброшены — потеря | серверные поля вне K(v) сброшены — потеря | соответствует |
| S4: обе стороны изменили поле из K(v) | правило категории: counter — сумма приращений и т. д. | значение сервера, приращение клиента потеряно | значение более поздней стороны, приращение другой потеряно | значение клиента, приращение сервера потеряно | значение более поздней стороны, приращение другой потеряно |
| S5: старый клиент удаляет запись с данными вне K(v) | tombstone, данные сохранены | обычное удаление — потеря (если нет конфликта версий) | обычное удаление — потеря | обычное удаление — потеря | обычное удаление — потеря |

Field-level LWW совпадает с критериями в S1–S3, но теряет данные в S4 (counter сливается как LWW,
а не сложением приращений) и в S5. Поэтому он служит контрольным вариантом: разница между ним
и адаптивным методом показывает вклад учёта версии схемы, а разница между ним и стратегиями уровня записи —
вклад перехода на уровень полей.

## Оракул

Оракул — независимая эталонная модель критериев S1–S5 (проект `Sync.Oracle`, зависит только от реестра схем).
На вход он получает начальное состояние и журнал событий в порядке доставки на сервер; у каждого события
есть автор, версия схемы, изменения полей и три момента логического времени: когда изменение сделано (`MadeAt`),
какое состояние сервера автор видел (`SeenAt`) и когда оно доставлено (`DeliveredAt`).

| Ситуация | Условие в оракуле | Эталонное значение |
| --- | --- | --- |
| S1 | автор на последней версии схемы, конфликта нет | значение клиента |
| S2 | автор старше, конфликта нет, поля вне K(v) не менялись после `SeenAt` | значение клиента; поля вне K(v) не меняются |
| S3 | автор старше, конфликта нет, поля вне K(v) менялись после `SeenAt` | значение клиента; поля вне K(v) сохраняют серверные значения |
| S4 | другой автор доставил изменение того же поля после `SeenAt` | counter — сумма приращений; user_owned/preference — входящее; server_authoritative — серверное; scalar — LWW по `MadeAt` |
| S5 | удаление автором старше, у записи есть непустые поля вне K(v) или связанные записи в новых таблицах | tombstone: запись помечена удалённой, данные и связанные записи сохранены |

Результат оракула — эталонное значение каждого поля каждой записи и признак удаления/tombstone; метрики
стратегий считаются сравнением их итогового состояния с этим эталоном.

## Адаптивный метод

Стратегия `Adaptive` (`Sync.Strategies/AdaptiveStrategy.cs`) решает по каждому полю операции и учитывает версию
схемы клиента. Вход тот же, что у базовых стратегий: версия схемы клиента и K(v), операция журнала с `base_row_version`
и логическим временем, снимок серверной записи со значениями, `field_versions` (`v` — `row_version` последней записи
поля, `t` — логическое время) и списком таблиц, где есть живые связанные записи.

1. Совместимость схем: клиент старше, если его версия меньше последней. Поля вне K(v) метод не пишет никогда:
   ни из изменений клиента (такие изменения отклоняются), ни значениями по умолчанию.
2. Конфликт по полю: поле изменено на сервере после того состояния, которое видел клиент
   (`field_versions[поле].v > base_row_version`).
3. Классификация изменения без конфликта: S1 — клиент последней версии; S3 — клиент старше и после
   `base_row_version` на сервере менялось хотя бы одно поле вне K(v); иначе S2. Значение клиента применяется.
4. Конфликт (S4) решается по категории поля: `counter` — серверное значение плюс приращение клиента
   (`new − old`); `user_owned`, `user_preference` — значение клиента; `server_authoritative` — значение сервера;
   `scalar` — LWW по логическому времени, при равенстве побеждает сервер.
5. Удаление клиентом старше последней версии превращается в tombstone (S5), если у записи есть поле вне K(v)
   со значением, отличным от умолчания, или живые связанные записи в таблице, появившейся после v. Запись помечается
   удалённой, все её значения и связанные записи сохраняются. Иначе — обычное удаление (S1/S2).
6. Исход операции: все изменения применены без правил — `Applied`; хотя бы одно поле решено правилом категории или
   отклонено, но что-то записано — `Merged`; ничего не записано — `Rejected`; удаление с сохранением данных — `Tombstoned`.
   Исход и ситуация по каждому полю пишутся в журнал операций сервера.

| Ситуация | Критерий (эталон) | Adaptive |
| --- | --- | --- |
| S1 | изменения клиента применены | применены |
| S2 | применены, поля вне K(v) не тронуты | применены только изменённые поля из K(v) |
| S3 | поля вне K(v) сохранены, изменения клиента применены | соответствует: пишутся только поля из K(v) |
| S4 | правило категории | соответствует: counter — сумма приращений, user_* — клиент, server_authoritative — сервер, scalar — LWW |
| S5 | tombstone, данные сохранены | соответствует |

Проверка: журналы из каталога `Sync.Simulation/OracleScenarios` (все примеры тестов оракула, включая смешанный
пример с клиентами v1/v2/v3) прогоняются через стратегию на модели сервера в памяти (`StrategyReplay`), и итоговое
состояние каждого поля, признаки удаления и tombstone, а также классификация S1–S5 совпадают с оракулом
(`OracleComparisonTests`). Базовые стратегии на тех же журналах расходятся с эталоном.

## Архитектура: метод как отдельный сервис

```
Клиент (SQLite) ──POST /sync──► Sync.Server (PostgreSQL: транзакция, блокировка, журнал операций)
                                     │  POST /resolve: версия схемы клиента, операция, снимок серверной записи
                                     ▼
                               Sync.Resolver (без состояния): ISyncStrategy → StrategyDecision
```

Сервер синхронизации отвечает за хранение, транзакции, идемпотентность и журнал, а решение по каждой операции
принимает сервис разрешения конфликтов. Сервер передаёт ему вход стратегии (версию схемы клиента, операцию
с `base_row_version` и снимок записи с `field_versions` и таблицами живых связанных записей) и применяет полученное
решение. Сервис ничего не хранит, поэтому метод заменяется другим сервисом с тем же контрактом без изменений
сервера и клиента. Для экспериментов та же стратегия может работать встроенной в сервер — это позволяет отделить
время работы метода от сетевых затрат.

## Мини-бенчмарк

Программа `adaptive-sync/src/Sync.Bench` прогоняет все стратегии на одних и тех же журналах и сравнивает результат
с оракулом. Запуск из `adaptive-sync/`: `dotnet run --project src/Sync.Bench -c Release -- ../docs/results 5`
(второй аргумент — число seed на конфигурацию). Результат — `docs/results/summary.md` и `docs/results/results.csv`.

**Сценарии.** Ручные журналы оракула (`OracleScenarios`) и журналы генератора `ScenarioGenerator` по seed:
4 профиля с предметами и модификациями, 6 клиентов, у каждого 4 сеанса работы офлайн; в сеансе клиент видит
состояние сервера на момент начала, делает N операций и доставляет их одним пакетом позже. Параллельно сервер меняет
поля (чаще — поля новых версий и поля категории `server_authoritative`). Параметры серий: доля старых клиентов
(0, 25, 50, 75 %; старые — поровну v1 и v2), конфликтность (доля операций над «горячей» записью и её первыми полями:
10, 30, 50 %), длина офлайна (1, 3, 6 операций). Генератор детерминирован: тот же seed даёт тот же журнал.

**Прогон.** Каждая стратегия работает на модели сервера в памяти (`StrategyReplay`), которая повторяет поведение
сервера синхронизации: `base_row_version` клиента — последняя версия, доставленная к моменту начала сеанса; собственные
записи клиента в пакете не считаются конфликтом, если поле не было оспорено чужим изменением (`OwnWrites`).

**Метрики** (эталон — оракул):

| Метрика | Определение |
| --- | --- |
| Потеря из-за несовместимости версий | доля «защищаемых» ячеек, итоговое значение которых отличается от эталона, плюс удаления S5 без tombstone. Защищаемая ячейка — поле записи вне K(v) клиента старой версии, который менял или удалял эту запись |
| Корректно применённые изменения клиентов | доля изменений полей клиентами в S1–S3, после которых значение поля совпало с эталоном на тот же момент журнала |
| Сохранённые данные сервера | доля ячеек, последним автором которых был сервер (или начальное состояние), с итоговым значением как в эталоне; защищаемые ячейки не входят |
| Конфликты (S4), решённые верно | доля конфликтных изменений, после которых значение поля совпало с эталоном (правило категории применено верно) |
| Расхождений с эталоном | число ячеек и признаков удаления/tombstone, отличающихся от эталона в итоговом состоянии |
| Время решения | среднее время вызова `Decide` на операцию, мкс; зависит от машины и не входит в проверку детерминизма |

**Итог первой версии** (59 сценариев, 3640 событий; полная таблица — `docs/results/summary.md`):

| Стратегия | Потеря из-за несовместимости версий | Изменения клиентов применены верно | Данные сервера сохранены | Конфликты решены верно |
| --- | --- | --- | --- | --- |
| Adaptive | 0 % (0/692) | 100 % | 100 % | 100 % (1313/1313) |
| Server Wins | 23,4 % | 74,1 % | 99,8 % | 32,4 % |
| LWW | 57,9 % | 83,9 % | 99,8 % | 58,3 % |
| Client Wins | 60,5 % | 100 % | 100 % | 49,3 % |
| Field-level LWW без схемы | 13,3 % | 99,9 % | 99,8 % | 65,6 % |

Стратегии уровня записи (LWW, Client Wins) теряют больше всего данных, неизвестных старым клиентам: запись
перезаписывается целиком. Server Wins не затирает такие поля, но теряет четверть изменений клиентов и отклоняет
большинство конфликтов. Field-level LWW без учёта схемы показывает вклад перехода на уровень полей, а разница между
ним и адаптивным методом (13 % → 0 % потерь, 66 % → 100 % конфликтов) — вклад учёта версии схемы и категорий полей.
Адаптивный метод совпадает с эталоном по построению: оракул и метод реализуют одни критерии S1–S5 независимо друг от
друга, и бенчмарк проверяет, что реализация метода через `field_versions` и `base_row_version` не теряет точности.

## Метрики без оракула

Чтобы результат не зависел только от эталона, который построен на тех же критериях S1–S5, что и метод, бенчмарк
считает показатели прямо по решениям стратегии и итоговому состоянию (`DirectMetrics`):

| Метрика | Определение |
| --- | --- |
| Записи в поля вне K(v) | число полей вне K(v) клиента, которые стратегия записала при обработке его операций (значения по умолчанию при перезаписи записи целиком); на 100 операций над живыми записями |
| Потерянные приращения счётчиков | Σ по ячейкам-счётчикам \|ожидаемое значение − итоговое\|, где ожидаемое — начальное значение плюс сумма всех приращений (клиентов и сервера), доставленных до удаления записи; в процентах от суммы приращений |
| Отклонённые операции и поля | доля операций (полей) клиентов над живыми записями, которые стратегия не применила |
| Удаления без tombstone | доля удалений клиентами старых версий записей, у которых есть значения в полях новых версий или живые связанные записи в новых таблицах, выполненных без tombstone |
| Исход `Merged` | доля операций, решённых правилами частично (признак автоматического разрешения конфликтов) |

Для счётчиков генератор задаёт изменения как приращения: «старое» значение клиента — состояние, которое он видел
в начале сеанса, плюс его собственные приращения в сеансе (`CounterDeltas`). Тогда ожидаемый итог счётчика
определяется журналом без оракула, и проверка тестом показывает, что он совпадает с эталоном оракула.

## Варианты метода (ablation)

Чтобы показать вклад каждой части метода, бенчмарк сравнивает полный метод с тремя упрощёнными вариантами
(`AdaptiveStrategy.WithoutSchemaVersion`, `WithoutCategories`, `WithRecordLevelConflicts`; на сервере не регистрируются):

| Вариант | Что убрано | Что теряется (базовая конфигурация, 30 seed) |
| --- | --- | --- |
| Adaptive-NoSchema | учёт версии схемы клиента | удаления старыми клиентами записей с новыми данными без tombstone — 100 %, потеря из-за несовместимости 6,1 % |
| Adaptive-NoCategories | правила категорий в S4 (всегда LWW) | верно решённые конфликты 66,5 % вместо 100 %, потерянные приращения счётчиков 8,9 % |
| Adaptive-RecordConflict | конфликт на уровне поля (конфликт по записи) | верно решённые конфликты 95,5 %, изменения клиентов применены верно 94,6 %, потеря из-за несовместимости 4,4 % |

Каждый вариант хуже полного метода хотя бы по одной метрике (проверяется тестом), то есть все три части метода —
учёт версии схемы, категории полей и уровень поля — дают вклад.

| Серия | Значения |

| Конфликтность | 0–60 % с шагом 10 % |
| Число клиентов | 2, 4, 6, 8, 12, 16, 20 |

## Сквозной замер: время синхронизации и объём данных

Режим `e2e` программы `Sync.Bench` измеряет синхронизацию на полном стенде: PostgreSQL 16 в Docker
(`docker compose up -d`), сервер синхронизации и resolver — отдельные процессы на Kestrel, запросы идут по HTTP
через loopback. Запуск из `adaptive-sync/`:

```
dotnet build AdaptiveSync.sln -c Release
dotnet run --project src/Sync.Bench -c Release --no-build -- ../docs/results 5 30 e2e 5
```

(последний аргумент — число seed; на каждый seed два сценария: базовая конфигурация и нагрузка с 20 клиентами,
20 профилями и офлайном по 6 операций). Для каждого режима создаётся отдельная база, между сценариями таблицы
очищаются, а последовательность версий сбрасывается; перед замером — прогревочный прогон.

**Клиент эмулируется на уровне протокола.** Каждый сеанс клиента из журнала — два запроса `/sync`: получение изменений
в момент `SeenAt` (без операций, `since_server_version` — последняя известная клиенту версия) и отправка пакета
в момент доставки. Операции пакета — те же объекты `SyncOperation`, что строит модель `StrategyReplay` (та же
`base_row_version`, логическое время и значения), поэтому итог на сервере можно сравнить с моделью побайтно.
Изменения сервера из журнала пишутся напрямую в PostgreSQL через `RecordStore` с очередной версией.

**Измерения.** Время запроса на стороне клиента (медиана и 95-й перцентиль), время обработки на сервере и суммарное
время решений метода по заголовку `Server-Timing` (`sync;dur`, `decide;dur;desc=<число решений>`), размер тела запроса
и ответа в байтах. Режимы: каждая стратегия, встроенная в сервер, и `Adaptive` через resolver.

**Проверка модели.** После каждого сценария состояние каждой записи в базе (значения всех полей, признак удаления,
`row_version`) и исход каждой операции сравниваются с моделью в памяти. На всех режимах и сценариях расхождений нет:
мини-бенчмарк и статистика (разделы выше) получены на модели, которая ведёт себя так же, как настоящий сервер.

Время синхронизации определяется работой с PostgreSQL (транзакция, блокировка записей, точки сохранения, журнал
операций), а не правилами метода: решение адаптивного метода занимает около 0,07 мс на пакет из 5 операций, меньше
0,2 % времени сервера, и по времени отправки метод не уступает базовым стратегиям. Вынос метода в отдельный сервис
добавляет сетевой вызов на каждую операцию — около 0,65 мс, или примерно 10 мс (≈ 25 %) к медиане отправки; это
цена заменяемости метода, и её можно снизить пакетным вызовом resolver. Объём данных у всех стратегий почти одинаков:
запрос несёт одни и те же операции, а ответ — состояние затронутых записей и изменения других клиентов.
